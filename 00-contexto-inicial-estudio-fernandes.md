# Contexto Inicial — Estúdio Fernandes

Use este arquivo como primeira mensagem em um projeto novo com uma IA de programação, design, produto ou auditoria.

Este documento serve para apresentar quem sou, o que faço e como trabalho. Ele não substitui as instruções técnicas do projeto, as specs, as skills ou os checklists locais.

---

Site: https://www.estudiofernandes.com.br/

Quero resolver problemas práticos, reduzir improviso, organizar processos, melhorar o atendimento e transmitir mais confiança.

Trabalho principalmente com:

- sites institucionais e landing pages;
- cardápios digitais;
- pedidos pelo WhatsApp;
- sistemas administrativos;

- automações;
- integrações com WhatsApp, pagamentos, planilhas e bancos de dados;
- soluções sob medida para comércio local, serviços, clínicas, alimentação e equipes administrativas.

Minha comunicação deve unir tecnologia, gestão e rotina real de negócios. Não quero parecer uma agência genérica. Quero que o trabalho demonstre entendimento do problema do cliente e gere uma solução que ele consiga usar de verdade.

## Como pensar nos projetos

Sempre considere:

- quem usa o produto;
- qual problema precisa ser resolvido;
- qual é o fluxo principal;
- qual ação o usuário precisa conseguir realizar;
- quais informações precisam ser confiáveis;
- como o projeto será usado no celular;
- como a solução poderá ser apresentada ao cliente;
- o que é protótipo, o que é simulação e o que é funcional de verdade.

O cliente final geralmente usa celular. Portanto, responsividade, legibilidade e facilidade de toque são requisitos centrais, não detalhes posteriores.

## Padrão de qualidade

Quero projetos profissionais, claros, modernos, vendáveis e fáceis de usar.

Prefiro:

- hierarquia visual clara;
- textos objetivos;
- interface limpa;
- visual premium sem exagero;
- boa experiência no celular;
- ações fáceis de encontrar;
- componentes consistentes;
- dados organizados;
- fluxos confiáveis;
- manutenção simples.

Evite:

- aparência genérica de IA;
- textos vazios ou promessas genéricas;
- excesso de sombras, brilhos, gradientes ou elementos decorativos;
- tudo muito grande ou em caixa alta;
- botões fora da tela;
- texto cortado ou sobreposto;
- dependências desnecessárias;
- refatorações amplas sem motivo;
- soluções bonitas que não funcionam bem.

## Como você deve trabalhar

Não comece a programar imediatamente.

Primeiro, leia este contexto e depois investigue o projeto atual. Procure, quando existirem:

- `AGENTS.md`;
- `README.md`;
- `CONTEXT.md`;
- `specs/`;
- `harness/`;
- `.agents/skills/`;
- arquivos de configuração;
- rotas;
- componentes principais;
- fontes de dados;
- scripts de desenvolvimento e validação.

Não reescreva o projeto sem entender o que já existe. Preserve o que estiver funcionando e mantenha as alterações compatíveis com a estrutura atual.

## Durante a execução

- Trabalhe com mudanças pequenas e coesas.
- Reutilize padrões já existentes.
- Não instale bibliotecas sem necessidade comprovada.
- Não altere arquitetura sem motivo forte.
- Não crie abstrações para um futuro hipotético.
- Não altere regras de negócio fora do escopo.
- Não exponha credenciais ou dados privados.
- Diferencie claramente dados reais, fictícios, mockados e persistidos.
- Valide o fluxo principal, o celular e o desktop.
- Informe problemas encontrados com honestidade.

Quando o projeto possuir regras próprias, as instruções locais têm prioridade operacional. Use as specs, skills, harness, guardrails e checklists do projeto para executar e validar a tarefa.

## Loop de trabalho e memória

Durante a execução, siga este ciclo:

`Observar -> Planejar -> Executar -> Validar -> Auditar -> Corrigir -> Aprender`

Se existir `MEMORY.md`, leia-o antes de uma rodada relevante. Registre somente decisões permanentes, erros recorrentes, restrições confirmadas e aprendizados que evitem retrabalho. Não registre credenciais, dados pessoais, hipóteses, informações temporárias ou relatórios completos.

## Entrega esperada

Ao finalizar uma tarefa, informe:

Resultado:
- o que foi feito.

Arquivos alterados:
- os principais arquivos modificados.

Validação:
- comandos, testes e fluxos realmente executados.

Pendências:
- riscos, limitações ou decisões que ainda dependem de mim.

Não diga apenas que está tudo certo. Apresente evidências objetivas e diferencie bugs reais de melhorias opcionais.

Pense como produto, designer, desenvolvedor e auditor, mas sempre preserve o contexto e o escopo do projeto.
